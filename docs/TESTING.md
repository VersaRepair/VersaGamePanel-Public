# First-time tester guide

**Goal:** Confirm that a new user can install VersaGamePanel, start one disposable game server, use its console, and recover its save data **using the public documentation alone**.

This is an **early alpha on a dedicated Linux amd64 Docker host** for trusted administrators. Docker socket access is effectively host-root; do not use a shared production host, real family worlds, or an internet-exposed admin interface.

**A first-time usability report is useful even when the software works.** Note any unclear terminology, unexplained prerequisite, missing step or control that did not behave as expected. No need to know the project's history or previous development process.

## Fast path: one clean install

1. Prepare a disposable Debian/Ubuntu amd64 VM with Docker Engine 26+ and Compose v2; Debian 13 is the tested baseline.
2. Follow the [Docker installation guide](CONTAINERS.md). Install using **Compose or docker run**, not both.
3. Confirm the container reports healthy with `docker compose ps` (if using Compose).
4. Open the panel through localhost or the documented SSH tunnel. **Do not forward port 8788 publicly**.
5. Retrieve the generated password locally, sign in as `admin` and change the password. Never include credentials in feedback.
6. Verify that the fresh panel has **zero servers**.
7. Choose one tested scenario from the [compatibility matrix](COMPATIBILITY.md); **Minecraft Java Vanilla 1.21.1** is the recommended first exercise.
8. Create and start a **disposable** game server. Accept any game EULA only after reading it and agreeing to its terms.
9. Wait for **real game readiness**, send a harmless console command, and confirm a response generated by the game—not simply text echoed in the browser.
10. Stop, restart, and verify files/settings/world state are retained. For backup/restore, use the scoped game-specific instructions below.
11. Report what worked, what failed, and where the instructions were confusing.

**Important:** Game ports default to localhost. Opening the panel through an SSH tunnel does **not** make a game joinable from another machine. Testing real remote multiplayer requires additional, explicitly controlled port bindings and networking.

## Before testing additional games

- [ ] Use trusted administrators, disposable data and a dedicated Docker VM.
- [ ] Check RAM, disk space and available TCP/UDP ports before downloading game runtimes.
- [ ] Explicitly prepare only the desired dedicated runtime (`unturned`, `terraria` or `tmodloader`) as described in the install guide. Runtime preparation downloads publisher software.
- [ ] Record the panel image digest, operating system, Docker/Compose versions, game version and any public mod IDs; do not upload environment dumps, world archives or secrets.
- [ ] For mods, establish a working unmodded game first. Local mod metadata inspection is not a malware scan or compatibility guarantee.

## Server and console checks

- [ ] Create a new game server with sensible limits and unused ports.
- [ ] Confirm the chosen game is actually ready, not just that its Docker container is running.
- [ ] Test start/stop/restart and observe the UI state.
- [ ] Send a harmless game command; confirm a genuine process-generated response.
- [ ] Disconnect and reconnect the console without stopping the game.
- [ ] If a suitable client is available, test joining the game; otherwise record **not tested** rather than claiming success.
- [ ] Check that the server retains configuration and save data after restart.

## Files, backups and restore

- [ ] Stop the disposable game before modifying save files or creating a consistent snapshot.
- [ ] Upload and download a harmless test file, checking its content is unchanged.
- [ ] Create a **Minecraft world backup** or a reviewed **Unturned/Terraria/tModLoader save snapshot**.
- [ ] Download an independent copy and keep it outside the panel's data volume.
- [ ] Change only disposable test data, restore the earlier snapshot and verify the previous state returns.
- [ ] Restart the game and confirm the restored world/save actually loads. For modded Terraria, check both `.wld` and `.twld`.

These are game-scoped snapshots, **not** guaranteed application, container-host or VM backups. Never risk a one-of-a-kind save to test restoration.

## Panel persistence (optional, Compose)

Only with disposable data: stop the game gracefully, retain a separate full-volume backup and run the following from the same Compose folder:

~~~sh
docker compose up -d --force-recreate
~~~

- [ ] Sign back in; an old session ending is expected.
- [ ] Verify accounts, server entries, save files and backups remain accessible.
- [ ] Verify the changed admin password still works.
- [ ] Confirm the disposable game starts with its previously saved state.

This does **not** certify a version-to-version upgrade or disaster-recovery rollback. `docker compose down` does not stop sibling game containers. Never use `down -v`, Docker prune or deleting volumes as an attempted fix.

## Report results

- [Report a reproducible bug](https://github.com/VersaRepair/VersaGamePanel-Public/issues/new?template=bug_report.yml).
- [Report a successful or failed compatibility test](https://github.com/VersaRepair/VersaGamePanel-Public/issues/new?template=compatibility_report.yml).
- [Report security problems privately](../SECURITY.md).

A useful report includes **host OS, Docker/Compose version, panel image digest, game/loader/mod version, exact steps, expected vs actual behavior**, and which checks were **passed / failed / not tested**. Call out anything a first-time user could not understand without outside help.

Manually redact all logs and screenshots. Never post passwords, tokens, cookies, Steam credentials, private URLs, player information, `users.json`, Compose secrets, whole data volumes or world archives.

After testing, stop and remove **only** your disposable servers, containers and volumes. Leave unrelated host resources untouched.
